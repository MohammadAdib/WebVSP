# AGENTS.md: how WebVSP is put together

A guide for coding agents and contributors. Read this before changing anything; it explains
where things live, how data moves, and the traps that are easy to fall into.

WebVSP is a fork of OpenVSP 3.55.0 that runs OpenVSP **entirely in the browser**, with OpenVSP's
**own GUI**. OpenVSP, its FLTK GUI and VSPAERO are compiled to WebAssembly and run in the tab.
Nothing in the page reimplements an OpenVSP screen: the FLTK GUI runs with its windows never
displayed, and a mirror serializes every window's widget tree to the page and applies the
page's input back to the real widgets. The page adds its own 3D view (three.js) and a VSPAERO
results viewer.

What changed and when: [CHANGES.md](CHANGES.md). User-facing docs: [README.md](README.md),
[web/README.md](web/README.md), [web/wasm/README.md](web/wasm/README.md).

## 1. The big picture

```
┌──────────────────────────────── the page (web/frontend, main thread) ────────────────────────────────┐
│  mirror/      OpenVSP's windows, drawn from widget JSON; input → mirror events                        │
│  viewport/    three.js 3D view: meshes, outlines, overlay, move gizmo, selection                      │
│  viewer/      VSPAERO results viewer (.adb)                                                           │
│  api/client.ts ── api.* calls ──► api/wasmEngine.ts  (loads the module, queues requests, polls take()) │
└──────────────────────────────────────────────┬────────────────────────────────────────────────────────┘
                                               │  call / take / takeBinary / mirrorEvent (thread-safe)
┌──────────────────────────────── vsp.wasm (web/wasm/engine/engine.cpp) ───────────────────────────────┐
│  OpenVSP's thread (PROXY_TO_PTHREAD): runs requests, pumps the FLTK GUI, watches the model            │
│      ▼                                                                                                │
│  OpenVSP (src/): geom_core (the model) · geom_api (VSP_Geom_API + Mirror* calls)                      │
│                  gui_and_draw (FLTK screens + WebMirror) · util (ProcessUtil → WebProcess)            │
└──────────────────────────────────────────────┬────────────────────────────────────────────────────────┘
                                               │  spawn requests (VSPAERO)
                              program.worker.js: vspaero.wasm / vsploads.wasm, one worker per run
```

## 3. How the GUI mirror works

The core idea: **never reimplement a screen.** If something in an OpenVSP window looks or
behaves wrong in the page, fix how it is mirrored (WebMirror.cpp / `mirror/*.tsx`), not the
screen.

### Engine → page

`WebMirror::Pump(timeout)` runs on OpenVSP's thread between requests: it applies queued page
events, runs the FLTK loop briefly, then `Diff()` walks every shown top-level window and emits
messages, which the page collects with `take()`:

- `{"t":"diff", full, windows, closed, widgets, removed}`: windows (`role` = `main`, `browser`
  for the Geom Browser, `geom` for geom editors, `screen` for other screens, `dialog`; plus
  designed size `dw/dh` and `rs` when FLTK lets it be resized) and widgets (id, parent, kind, rect, label, colours, value, state,
  bound parm, kind-specific fields like menu items, tree items, browser lines, table cells,
  GL draw objects, SVG for plots). Only changes are sent unless `full`.
- `{"t":"dialog", seq, kind, ...}`: a prompt (`choice`, `alert`, `message`, `file`). Choices and
  file choosers block OpenVSP's thread (still pumping) until the page answers. File choosers
  are answered by `wasmEngine.ts` with the browser's pickers (marked `native`); the others are
  drawn by `Dialogs.tsx`.
- `{"t":"overlay", objs}`: what the main 3D view shows besides the model (§5). At most every
  200 ms, only when changed.

`wasmEngine.ts` wraps them as `{type: 'mirror', msgs}` events for `App.tsx`; a full snapshot is
requested when the page connects (`requestFull`).

### Page → engine

`sendMirror(event)` (`mirror/store.ts`) posts flat JSON events (numbers and strings) through
`mirrorEvent`, applied by `ApplyEvent()` in WebMirror.cpp. Ops: `set` (value + callback),
`click`, `check`, `pick` (menu item), `tab`, `browser`, `tree_icon`, `text`, `key`, `mouse`
(replayed mouse events, for trees/canvases/GL views), `resize`, `close`, `dialog` (prompt
answers), `full`.

### Page side

`mirror/store.ts` holds windows and widgets by id and children by `win:parent`.
`Widgets.tsx` draws each widget at its exact FLTK position with a component per `kind`.
`Window.tsx` draws floating windows (with resize grips when `rs`: resizing sends `resize`, and
the real window re-lays itself out, never below `dw/dh`) and handles menu shortcuts;
`Dock.tsx` the side panels. The
left panel shows the `browser` window and the right one the first docked editor (`isDocked` in
`App.tsx`: `geom` windows except Group Modifications, and the Vehicle screen). Resizing a panel
resizes the real FLTK window so it re-lays out.

## 4. Requests, events and model changes

The page calls `api.*` (`client.ts`) → `wasmRequest(method, path, body)` (`wasmEngine.ts`), which
maps routes to engine ops (`call(id, op, a, b, value)`); results come back through `take()`
(JSON) or `takeBinary(id)` (meshes). Engine ops: `model`, `geomTypes`, `bbox`, `mesh`,
`addGeom`, `deleteGeoms`, `setParm`, `move`, `rotate`, `drawType`, `duplicate`, `origin`, `newModel`, `readFile`, `writeFile`,
`pick`. Most editing happens through the mirrored GUI, not the API.

Model changes:

1. The user edits through a mirrored widget, or the page calls an op.
2. OpenVSP updates.
3. The engine's watcher polls `GetAndResetUpdateCount()` and a tree signature, fingerprints each
   geom's parm values (a child includes its parent's, since it moves with it), and emits
   `{"type":"model_changed", rev, tree, changed, removed}`.
4. `store.handleEvent` bumps `meshRev[id]` for changed geoms and reloads the tree if needed.
5. `GeomMesh` refetches its mesh when its `meshRev` changes.

Selection is OpenVSP's: the tree's `active` list comes from `GetActiveGeoms()`. Clicking in the 3D
view calls `api.pick(id, toggle)` → `MirrorPickGeom` → `ManageGeomScreen::Set` / `Toggle`, so the
Geom Browser and editors follow.

### Files

The module has an in-memory file system; the user's files live in `/home/web_user`. GUI file
choosers are answered by `answerFileDialog` (`wasmEngine.ts`) with the browser's pickers: opened
files are copied in, and every opened or Save-As'd file is **linked** to the file on disk (its
`FileSystemFileHandle` in Chrome/Edge). `watchLinked` notices whenever OpenVSP writes a linked
file (Save, Save As, Ctrl+S) and, once it stops changing, writes it back through the handle
(asking for readwrite permission, which Chrome grants per file) or downloads it.

### Mesh payload (`VSPM`)

Written by `MeshBytes` (`engine.cpp`), read by `decodeMesh` (`api/mesh.ts`, which documents the
format): surfaces as u/w grids (or a triangle list for Mesh Geoms), then the outline (feature
line segments from `MirrorFeatureLines`), then per-surface parts for Mesh / NGon Mesh geoms.
Those come from the geom's own wire/shade draw objects (`TagSurfaces` in `engine.cpp`, which
includes geom_core headers directly): one surface per tag, its colour-wheel colour when the
desktop colours it (always for NGon meshes; Mesh geoms drawn by tag), and the tag's polygon
edges for NGon meshes. Last, a flag per surface (bit 0: a disk, `DISK_SURF`, drawn at
`DISK_ALPHA` when shaded). **Change the writer and the reader together.**

## 5. The 3D view (`viewport/`)

- **Surfaces**: per geom, shaded mesh + u/w grid lines + outline (drei `Line`). Draw type per
  geom from the Geom Browser (wire / hidden / shade / none). Mesh / NGon Mesh tags get their own
  materials: shaded in a tint of the tag colour, edges in the colour (NGon meshes draw their
  polygon edges, not the triangles').
- **VSPAERO's geometry**: Launch Solver leaves an NGon mesh (`MeshGeom_NGon`) of what it solved
  on, shown, as the desktop does; control surfaces in a used group are tags of their own.
- **Overlay**: `MainOverlayJson()` in WebMirror.cpp sends draw objects the page doesn't get
  from meshes:
  - the screens' own draw objects (main GL window's objects minus the vehicle's), such as the
    Mass Properties CG;
  - from the vehicle's geoms: anything whose `m_GeomID` starts with `BBOXHEADER` (selection
    and wing-section boxes, tagged `box: 1|2`) or `XSECHEADER` (cross sections, skinning and
    blending vectors), hinge geoms whole, and **blank geoms as `{"t":"blank", id, sel, p}`
    markers** (drawn as clickable HTML circles).
  Visibility follows OpenVSP's own `m_Visible`, so the page shows what the desktop shows.
  Overlay items are drawn on top (no depth test).
- **Move gizmo** (`MoveGizmo`): drei `TransformControls` on an empty object at the mean of the
  selected origins (`api.geomOrigin`). Dragging only offsets the drawn meshes
  (`usePreview`); on release `api.moveGeoms(ids, delta)` → `MirrorMoveGeoms`, which
  converts the world delta into each geom's abs/rel location frame, skips geoms that follow a
  selected ancestor, and sets the parms inside one undo group. `keepArrowsOutward` patches the
  gizmo so arrows always point +X/+Y/+Z and thickens its axis lines.
- **Clicks**: a click on a mesh picks it; Shift/Ctrl/Cmd toggles; a click on nothing (not a
  drag, not on the gizmo) deselects.
- **Blender keys** (`mirror/blenderKeys.ts`): A, Alt+A, H, Shift+H, Alt+H press the Geom
  Browser's own buttons (Sel All, NoShow, Show Only, Show) or pick nothing, so they act on the
  whole selection exactly as the buttons do; Alt+H first adds the hidden geoms to the selection,
  then presses Show. Z / Shift+Z set draw types through `api.setDrawType` (engine `drawType`).
  Shift+D: `api.duplicateGeoms` (engine `duplicate` → `MirrorDuplicateGeoms` →
  `Vehicle::DuplicateGeomVec`, which copies with `CopyGeomVec` and puts each copy under its
  original's parent; the clipboard is untouched), then `startTransform('move', copies)`.
  X / Delete: `askDelete` (`mirror/DeleteConfirm.tsx`, an "are you sure" prompt that holds the
  keyboard while open), then the Geom Browser's Delete (OpenVSP's own delete and clone prompt).
  The listener runs in the capture phase so that while G / R runs, its keys (X, digits, R...)
  never reach the view keys or OpenVSP's menu shortcuts; plain R replaces OpenVSP's
  View > Set Rotation Center shortcut. `viewport/KeysHelp.tsx` lists the keys (the floating
  keyboard button by the toolbar); keep it in step.
- **G / R** (`viewport/transform.tsx`): `useTransform` holds the run (mode, ids, their origins,
  locked axis, typed value, mouse result); `TransformDriver` in the active pane turns mouse moves
  into a move (in the view plane through the selection, or along the locked axis as drawn on
  screen) or an angle (around the selection on screen); `TransformAxisLine` draws the locked
  axis; `TransformHud` shows the value. The preview (`usePreview`, shared with the move gizmo)
  only moves the drawn meshes (`previewMatrix`), until each geom's new mesh arrives. Applying calls
  `api.moveGeoms` or `api.rotateGeoms` → `MirrorRotateGeoms`, which turns each model matrix about
  the geom's own origin and converts it back to its abs/rel location and rotation as
  `GeomXForm::ComposeModelMatrix` does, in one undo group.
- **Camera**: `camera.tsx`, shared with the results viewer. View requests wait until the orbit
  controls are bound to the current camera, the camera is of the requested projection and the
  view has a size; a new camera only inherits the pose of one that was framed. Moves to a view
  are animated (`go`, `blendDirection`: elevation and azimuth separately, `VIEW_MOVE_MS`); the
  first framing snaps, and a mouse drag stops a move. Fitting (`fit`, F) puts the model's
  bounding sphere across `FIT_SCALE` of the view's shorter side; `center` (C, View > Center and
  Center All through `VIEW_ITEMS` in `mirror/Window.tsx`) only pans to the model, keeping the
  zoom. Numpad 4 / 6 / 8 / 2 turn `ORBIT_STEP` (30°); 8 / 2 step the elevation, held within
  `MAX_ELEVATION` (Z stays up, so the view can't go over a pole). `StableOrbitControls` keeps
  one set of orbit controls for the life of a pane and hands it the new camera on a projection
  switch, so a drag carries on across it. An orthographic camera keeps its framing when the view
  resizes.
- **Auto perspective**: each pane's `autoOrtho` (`withView` in `Viewport.tsx`): axis views
  (`AXIS_VIEWS`) switch to orthographic, turning away (`OFF_AXIS_VIEWS`, or `RotateWatch` as soon
  as the mouse turns the view) goes back to perspective only if it switched automatically; 5 or
  the projection button clears it. The orientation gizmo's balls go through `onAxisView` (our
  views, not drei's animation).
- **Panes**: `Viewport` splits into one, two or four panes (`layout` in the store, remembered),
  each its own `<Canvas>` with its own camera and `Scene`. View choices (toolbar, keys, the View
  menu through `viewRequest`) go to the active pane; `refitAll` (a model loaded or replaced)
  frames the model in every pane from its own view. Meshes are fetched once for panes asking
  together (`fetchMesh`); per-pane frame state goes through `PaneViewContext`. Changing the
  layout fades the panes out and in (`changeLayout`, `LAYOUT_FADE_MS`, `LAYOUT_SETTLE_MS`), with
  no input meanwhile.
- **Grid**: `GroundGrid`, plain line segments rebuilt when the zoom level changes: the finest
  round spacing at least `GRID_MIN_PIXELS` apart plus the next (10x) brighter, the finer fading
  out; red X / green Y axes; fades out from the model's footprint to `GRID_FADE_END` times it.
  The footprint is every geom's, hidden ones too (`api.bboxAll`, engine `bbox` with a="all").
- **Menus**: `buildMenu` (`mirror/Window.tsx`) leaves out `HIDDEN_ITEMS` (File > Preferences:
  the page always uses the browser's file pickers).

## 6. VSPAERO

- `vspaero` and `vsploads` are separate WebAssembly programs (built with `-Targets
  vspaero,vsploads`). `ProcessUtil` (under `__EMSCRIPTEN__`) asks the page through
  `WebProcess`; `wasmEngine.ts` `runProgram` starts a `program.worker.js` per run, copies the
  working files in, streams output back (`processOutput`), copies written files back and reports
  the exit (`processExit`). The engine creates placeholder files `/bin/vspaero` etc. and calls
  `SetVSPAEROPath("/bin")` so OpenVSP finds them. Single-threaded (no OpenMP).
- **Run timer**: `api/solverRun.ts`. A run lasts while the VSPAERO window's Kill Solver button
  is active (watched in `mirror/Window.tsx`, `setSolverRunning`) and counts only if `vspaero` was
  launched during it (the button flickers on as the window appears); `vspaero`'s exit code says
  how it ended. `SolverTimer` shows it in that window's title bar.
- **Results viewer**: `vspviewer` launches are intercepted by `openViewer` in `wasmEngine.ts`,
  which reads `<base>.adb`, `.adb.cases` and `.polar` and opens `viewer/ResultsViewer.tsx`. Its
  wakes are drawn past their end and faded out (`WAKE_FADE_LENGTH`, `WAKE_FADE_STEPS` in
  `buildWakes`) instead of the desktop viewer's infinite wakes. The
  `.adb` layout is checked against the writers in `src/vsp_aero/Solver/VSP_Solver.C` (magic
  `-123789456`, +3 for v3).

### Releasing

A push to `main` that touches `src/`, `Libraries/`, `web/` or the workflow is the whole release:
`pages.yml` builds the engine (Linux; Emscripten and CMake pinned in `EMSDK_VERSION` and
`CMAKE_VERSION`; `build_wasm.ps1` under PowerShell 7), then the page with that engine in it,
then deploys to GitHub Pages. Nothing is built or uploaded by hand, so any clone can release.

- The libraries and FLTK are cached (keyed on `Libraries/`, `web/wasm/fltk/`, the toolchain and
  the build script); OpenVSP compiles through ccache. A first or library-changing run rebuilds
  everything (about 10 minutes); an ordinary push rebuilds only what changed.
- Building on Linux turned up library quirks the Windows build never hit, now handled for
  WebAssembly builds: delabella adds `-mfma` on x86-64 hosts (so it also gets `-msimd128`), and
  Eigen builds a Fortran LAPACK when a Fortran compiler is around (so only its headers are
  installed). Older CMake versions read FLTK's type-size checks wrongly, hence the pinned CMake.
- `workflow_dispatch` runs it on any branch (builds everything; only `main` deploys).
- Changing the Emscripten version: update `EMSDK_VERSION` (and `CCACHE_COMPILERCHECK`) in the
  workflow, and the version in `build_wasm.ps1`'s comment.

## 8. Conventions and traps

- **Repos and branches.** One branch, `main`, tracking `origin` (`MohammadAdib/WebVSP`); pushing
  it deploys. `upstream` is OpenVSP itself, for pulling its releases: **never push to it** (its
  push URL is disabled). `MohammadAdib/WebVSP` is a GitHub fork of `OpenVSP/OpenVSP`, so GitHub
  compares it with upstream and can sync OpenVSP's new commits.
- **Commits**: only when asked; no AI co-author or "Generated with" lines.
- **Threading.** All OpenVSP calls happen on OpenVSP's pthread in the module. The page reaches
  it only through the exported, thread-safe functions; WebMirror's `PostEvent` and
  `TakeOutput` are its thread-safe entry points.
- **Adding an operation**: the API function (C++, `VSP_Geom_API.{h,cpp}` with a doc comment), an
  `op` in `engine.cpp` `Run()` and its header comment, a route in `wasmRequest`
  (`wasmEngine.ts`), and `api.*` in `client.ts`. Rebuild the engine.
- **Undo.** The page's undo is OpenVSP's parm undo (Edit > Undo, through the mirrored menu).
  Parms set with `Set()` are not recorded; use `SetFromDevice()` like the GUI does, inside
  `BeginUndoGroup`/`EndUndoGroup` when one user action changes several parms.
- **zustand selectors** must return stable values: use shared empty constants (`NO_GEOMS`,
  `NO_IDS`) instead of `?? []`, or the component re-renders forever.
- **Line endings.** Some files are CRLF and some LF. Edit tools handle it; scripted edits must
  preserve the file's existing endings.
- **Shell.** Bash heredocs mangle backslashes: write files containing `\t`, `\n`, `\\` with an
  editor tool, not a heredoc.
- **WebGL lines are 1 px.** For thicker lines use drei `Line` (Line2) or meshes.

## 9. Not supported yet, and known OpenVSP issues

- STEP export (`VSP_NO_STEP`), multithreaded VSPAERO, CalculiX, the desktop VSPAERO viewer (the
  page's viewer replaces it).
- The page's results viewer: control surfaces, rotors, cut planes, coarse mesh levels, surface
  selection, export.
- OpenVSP (desktop too) doesn't save NGon mesh data to `.vsp3` files (`NGonMeshGeom::EncodeXml`
  writes an empty node), and Mesh > Other > Convert to NGon Mesh on a Mesh loaded from a file
  crashes; in the browser that crash stops the engine. Converting a Mesh made in the session
  works.
